# 025. 数据分层架构与状态管理协同

随着应用复杂度提升，合理的数据分层架构能够帮助我们应对多数据源、离线缓存、错误恢复等挑战。本节梳理 Repository 分层模型、数据同步策略与错误处理思路，并展示如何与常见状态管理方案融合。

## 数据分层的典型结构

```
Presentation Layer (Widget / ViewModel / Controller)
        ↓
Repository Layer (Use cases, Aggregation, Caching)
        ↓
Data Sources
  ├── Remote Data Source (REST / GraphQL / gRPC)
  ├── Local Cache (SQLite / Hive / SharedPreferences)
  └── Device Services (传感器、文件系统等)
```

### Repository 角色

- **抽象数据来源**：屏蔽远程与本地实现细节，给上层暴露统一 API。
- **组合策略**：根据业务需求决定数据读取顺序（先缓存、先远程、并行等）。
- **业务规则内聚**：在 Repository 层处理权限、过滤、排序等业务逻辑。
- **错误归一化**：将底层异常转换成领域可识别的错误类型，便于 UI 处理。

### 数据源职责

- **RemoteDataSource**：只关心网络协议与 DTO（数据传输对象），不混入业务逻辑。
- **LocalDataSource**：负责持久化与缓存策略，提供 CRUD 接口。
- **DeviceDataSource**：封装设备相关服务（如定位、剪贴板）。

## 数据同步策略

1. **Cache-First**：优先返回本地缓存，随后刷新远程数据。适合用户体验要求高的场景。
2. **Network-First**：先尝试网络请求，失败时回退到本地缓存。适用于对实时性要求高的场景。
3. **Stale-While-Revalidate**：先返回缓存的旧数据，再异步刷新并推送更新。常见于时间线、列表数据。
4. **Write-Through**：写入时同时写本地和远程，确保数据一致；若远程失败则回滚或标记重试。
5. **Sync Queue**：离线场景将变更写入队列，恢复网络后逐条重放，结合重试策略确保最终一致。

### 同步实现要点

- **版本字段**：维持 `updatedAt` / `version` 用于增量同步。
- **变更日志表**：记录用户离线操作，便于恢复与冲突解决。
- **冲突处理**：定义优先级（客户端 vs 服务端）、合并规则或用户确认流程。
- **监控反馈**：同步失败时及时上报与提示，防止数据丢失。

## 错误处理与恢复

- **错误分类**：网络异常、认证失败、业务校验失败、不可恢复错误（如 schema 不兼容）。
- **统一异常模型**：定义 `AppError` / `Failure` 等类型封装底层异常，提供 `code`、`message`、`retryable` 信息。
- **重试策略**：
  - 可重试错误使用指数退避和最大重试次数限制。
  - 对幂等接口可自动重试，非幂等接口需谨慎处理。
- **用户反馈**：将错误转化为可理解的提示，可提供“刷新”“重试”按钮或离线模式入口。
- **日志与上报**：集中处理错误日志，辅以远程日志或崩溃分析平台定位问题。

## 与状态管理的结合示例（以 Riverpod 为例）

### 定义 Repository 接口与实现

```dart
abstract class ArticleRepository {
  Stream<ArticleState> watchArticles();
  Future<void> refresh();
}

class ArticleState {
  const ArticleState({
    required this.items,
    required this.isLoading,
    this.error,
  });

  final List<Article> items;
  final bool isLoading;
  final AppError? error;

  ArticleState copyWith({
    List<Article>? items,
    bool? isLoading,
    AppError? error,
  }) => ArticleState(
        items: items ?? this.items,
        isLoading: isLoading ?? this.isLoading,
        error: error,
      );
}

class DefaultArticleRepository implements ArticleRepository {
  DefaultArticleRepository(this._remote, this._local);

  final RemoteDataSource _remote;
  final ArticleDao _local;

  @override
  Stream<ArticleState> watchArticles() async* {
    final cached = await _local.list();
    yield ArticleState(items: cached, isLoading: true);

    try {
      final remote = await _remote.fetchArticles();
      await _local.upsertMany(remote);
      yield ArticleState(items: await _local.list(), isLoading: false);
    } on NetworkException catch (error) {
      yield ArticleState(
        items: cached,
        isLoading: false,
        error: AppError.network(error.message),
      );
    } catch (error) {
      yield ArticleState(
        items: cached,
        isLoading: false,
        error: AppError.unexpected(error.toString()),
      );
    }
  }

  @override
  Future<void> refresh() async {
    final remote = await _remote.fetchArticles();
    await _local.upsertMany(remote);
  }
}
```

### Riverpod Provider 组合

```dart
final articleRepositoryProvider = Provider<ArticleRepository>((ref) {
  final remote = ref.watch(remoteDataSourceProvider);
  final local = ref.watch(articleDaoProvider);
  return DefaultArticleRepository(remote, local);
});

final articleStateProvider = StreamProvider<ArticleState>((ref) {
  final repository = ref.watch(articleRepositoryProvider);
  return repository.watchArticles();
});
```

在界面层消费：

```dart
class ArticleListPage extends ConsumerWidget {
  const ArticleListPage({super.key});

  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final asyncState = ref.watch(articleStateProvider);

    return asyncState.when(
      data: (state) {
        if (state.items.isEmpty) {
          return const Center(child: Text('暂无数据'));
        }
        return RefreshIndicator(
          onRefresh: () => ref.read(articleRepositoryProvider).refresh(),
          child: ListView.builder(
            itemCount: state.items.length,
            itemBuilder: (context, index) {
              final article = state.items[index];
              return ListTile(
                title: Text(article.title),
                subtitle: Text(article.summary),
              );
            },
          ),
        );
      },
      loading: () => const Center(child: CircularProgressIndicator()),
      error: (error, stackTrace) => ErrorView(
        message: (error as AppError).displayMessage,
        onRetry: () => ref.read(articleRepositoryProvider).refresh(),
      ),
    );
  }
}
```

- `StreamProvider` 自动管理订阅与状态刷新，UI 层无需感知数据源细节。
- `ErrorView` 接收标准化的 `AppError`，实现统一的错误展示与重试入口。

## 跨模块的一致性策略

1. **定义统一的 Result 类型**：如 `Result<T>` / `Either<Failure, T>`，提高错误处理的可组合性。
2. **可观测的数据流**：使用 `Stream`、`StateNotifier`、`Bloc` 等形式，将数据变化主动推送给 UI。
3. **依赖注入**：利用 `Provider`、`get_it` 或服务定位器管理 Repository 与 Data Source 的生命周期，方便测试与替换。
4. **可测试性**：为每层编写单元测试，模拟远程、本地数据，在 CI 中保障同步逻辑的正确性。

## 总结

- Repository 分层能显著降低模块耦合度，让业务逻辑集中化、可维护。
- 合理的数据同步策略是提升离线体验、保障数据一致性的关键。
- 统一的错误模型与重试机制，让用户在网络波动或系统异常时仍能获得可预期的反馈。
- 将 Repository 与状态管理工具结合，可以构建出响应式、健壮且可测试的应用数据层。
